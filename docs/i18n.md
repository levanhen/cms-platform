# Multi-language (i18n) – Future Extension

| Field | Value |
|---|---|
| Status | **Future** — not implemented in the MVP |
| Locales | `vi` (source), `en` (translation) |
| Related | [overview.md](./overview.md), [requirement.md](./requirement.md), [data-model.md](./data-model.md), [web-frontend.md](./web-frontend.md), [multi-site.md](./multi-site.md) |

> Current MVP: **a single language** (content + UI chrome mostly in Vietnamese).  
> This spec **locks in the extension direction** to avoid the wrong refactor when the i18n phase begins.  
> **Not the same as multi-site:** i18n = multiple languages on the same website; multiple domains/brands → [multi-site.md](./multi-site.md).

---

## 1. Goals

The public Web supports **2 languages: VI and EN**.

- Content is authored **in Vietnamese first** (source / default language).
- The **EN** version is created through a **Translate** flow from the VI version — editors are not required to fill in two parallel forms from scratch.
- Simpler management: VI is always the "source of truth"; EN is a trackable translation.

---

## 2. Agreed principles

| Principle | Details |
|---|---|
| Source locale | `vi` — required when creating content |
| Target locale | `en` — translation; may be missing / Draft / Published independently |
| Workflow | **Translate**, not parallel dual-editing |
| BO UI chrome | Stays in Vietnamese (form labels); field content follows the locale being edited |
| Web chrome | VI / EN switcher; static UI strings are translatable (nav, buttons) |
| Fallback | EN not Published → fall back to VI content **or** EN 404 (decided at implementation; recommended: fall back to VI + optional "Chưa có bản EN" (No EN version yet) badge) |
| Settings | Public text can be translated (e.g. `site_description`, contact copy); technical keys (`max_upload_size_mb`) are not translated |

---

## 3. BO flow (Translate)

```text
1. Editor creates / edits the VI version → saves as Draft or Publishes
2. Selects "Dịch sang EN" (Translate to EN)
      → creates an EN translation record (copies text fields from VI as a starting point)
3. Editor edits EN → Draft / Publish independently
4. Unpublishing / archiving EN does not require unpublishing VI
```

Suggested UI:

- On the content form: a **VI | EN** locale switcher (EN disabled until "Translate" has been run).
- Translation status: `Missing` | `Draft` | `Published` (for EN).
- No AI required in the first phase; manually copying from VI is sufficient. AI translation = optional later.

Applicable modules (same pattern): Pages, Services, Projects, News (+ category/tag names if needed).  
Documents: title/description metadata can be translated; the binary file is usually shared.

## 4. Data model (proposed — not migrated)

Two acceptable approaches; **A is recommended**.

### A. Translation table / JSON per entity (recommended)

- The base record holds identity + status lifecycle + shared media.
- Per-locale text lives in `translations` (a child table or structured JSON):

```text
content (page | service | project | news …)
  id, status, featured_image, …
  translations[]
    locale          vi | en
    slug            unique per locale (or unique (locale, slug))
    title / name
    summary / excerpt / …
    content HTML
    seo_title, seo_description
    translation_status   (optional) draft | published
    updated_at
```

- `locale = vi` always exists after creation.
- `locale = en` only exists after Translate.

### B. Record per locale + group id

- One row per locale; `translation_group_id` links the versions.
- More complex for publishing/listing; choose only if the team is familiar with this pattern.

**Current MVP:** single-language schema (no locale column) — treat all existing data as `vi` when migrating later.

## 5. Web routing (proposed)

| Approach | Example | Notes |
|---|---|---|
| Locale prefix | `/vi/services/...`, `/en/services/...` | Explicit, good for SEO |
| Default VI without prefix | `/services/...` = VI; `/en/services/...` = EN | Shorter if VI is the primary market |

Recommendation: a **`[locale]` segment** with default `vi`; middleware sets the locale; hreflang + sitemap per locale.

Redis keys: include the locale, e.g. `web:news:en:{slug}`, `web:settings:public:en`.

---

## 6. Multilingual public settings

Public text keys (future):

- `site_name`, `site_description`, SEO defaults, `contact_address` (if needed), slogan…

Options:

- `settings` value shaped as `{ "vi": "...", "en": "..." }`, or
- a `_en` key suffix / a `setting_translations` table.

The `default_language` setting = `vi` (source). It is not used to "turn off" VI.

---

## 7. Acceptance (when implementing the i18n phase)

- [ ] Creating content requires a VI version.
- [ ] Translate creates an EN version from VI; EN can be edited independently.
- [ ] Publishing VI does not require an EN version to exist.
- [ ] Web locale switcher; URLs distinguish locales.
- [ ] Published EN displays correctly; Draft EN is not exposed on the web.
- [ ] Redis cache / revalidation per locale.
- [ ] Sitemap / hreflang cover all Published locales.
- [ ] Migration from MVP data = everything mapped to `vi`.

---

## 8. Not in the MVP

- Implementing the locale schema / Translate UI.
- Requiring editors to enter EN when creating content.
- Automatic AI translation (may come in a phase after i18n).
